# 11. Build the cloud-init seed and attach it as a virtio disk

Date: 2026-08-31

## Status

Accepted

Narrows [ADR-0009](./0009-orchestrate-existing-host-cli-tools.md) (orchestrate
existing host CLI tools) in one place, and follows from
[ADR-0004](./0004-direct-kernel-boot-with-copy-on-write-overlays.md) (direct
kernel boot), which is what leaves an aarch64 guest without the firmware that
would otherwise carry the seed's location.

## Context

Until now the seed was `virt-install --cloud-init`'s to build: it wrote a
NoCloud ISO from the user-data we generated, filled in the meta-data itself,
attached the ISO for the first boot, and left it out of the XML it defined.
That is exactly the division of labour ADR-0009 asks for, and on x86_64 it
works.

On aarch64 it produces a VM that boots and can never be logged into.

The `virt` machine type has no IDE or SATA bus, so virt-install attaches the
seed as a USB CD-ROM (`bus='usb'`, `model='usb-bot'`). USB mass storage is
enumerated late: the device is found at about 1.0s, the `usb-storage` driver
binds at 1.7s, and the SCSI CD-ROM behind it appears at 2.7s, because the probe
carries a one-second device-reset delay. cloud-init's local stage — where the
datasource is chosen — runs at about 1.6s. It finds no filesystem labelled
`cidata`, concludes `DataSourceNone`, and the boot continues with no login user
and no authorized key:

```
[    1.662159] usb-storage 2-1:1.0: USB Mass Storage device detected
[    2.686678] sr 0:0:0:0: Attached scsi CD-ROM sr0
cloud-init ... running 'init-local' ... Up 1.63 seconds.
cloud-init ... finished ... Datasource DataSourceNone.
```

The usual second hint is missing too. virt-install writes `ds=nocloud` into the
SMBIOS system serial, but a directly booted kernel on `virt` has no firmware and
therefore no DMI (`DMI not present or invalid`), so nothing reads it. The guest's
own `datasource_list` still names NoCloud, so ds-identify selects it — the
datasource simply finds no device to read.

`create` then fails at the SSH wait with `Permission denied (publickey)`, which
names the symptom and not the cause.

Three ways out were considered.

**Wait for the device.** Order `cloud-init-local.service` after
`systemd-udev-settle.service` in each distro's `Containerfile`. It is a small
change and touches no contract, but it makes a timing problem depend on a
deprecated unit, and it delays every boot on every architecture to fix one
architecture's bus.

**Ask virt-install for a different bus.** There is no option for it.
`--cloud-init` chooses the bus from the machine type, and `--xml` XPath edits
apply to the XML virt-install defines, which by design no longer contains the
seed. This was tried on a real aarch64 host: the device stayed USB.

**Build the seed ourselves and choose the bus.** `virt-make-fs` — already a
required tool, used to build every base image — writes a vfat filesystem
labelled `cidata` from a directory, and `--disk ...,bus=virtio` attaches it
beside the root disk.

## Decision

Build the NoCloud seed with `virt-make-fs` and attach it as a read-only virtio
disk.

- The VM's state directory gains a `seed/` directory holding the two files
  cloud-init reads — `user-data` (still generated by `internal/guestinit`) and
  `meta-data` (now generated there too) — and `seed.img` built from it.
- `virt-install` is passed `--disk path=<seed.img>,format=raw,bus=virtio,
  readonly=on` and no longer `--cloud-init`.
- The instance id in `meta-data` is the VM name: stable across reboots, so
  cloud-init does not rerun per-instance modules on a VM that is in use, and
  unique among the VMs on a host.

virtio-blk is probed with the root disk, so the seed is present well before
cloud-init looks for it — on both architectures, for the same reason.

## Consequences

**What this buys.** aarch64 hosts work. The seed's arrival no longer depends on
bus enumeration order, on a machine type's device model, or on DMI being
present, so the same mechanism is exercised on every architecture instead of one
path being x86-only. The seed is a plain file in the VM's state directory,
inspectable with `virt-ls` or a loopback mount, which the transient ISO in
`/var/lib/libvirt/boot` — unlinked as soon as the domain started — was not.

**What it costs.** Two things virt-install did are now ours: composing
`meta-data`, and knowing that NoCloud wants a filesystem labelled `cidata`. Both
are small, both are pinned by golden files, and neither is a reimplementation of
a tool — `virt-make-fs` still writes the filesystem. This is the narrowing of
ADR-0009 that this record exists for: the tool that built the seed could not be
told where to attach it, so it builds the filesystem and we attach it.

**The seed outlives the first boot.** virt-install's ISO was removed from the
domain once it had booted; this disk stays attached for the life of the VM, and
`vdb` is visible inside the guest. It is read-only, and it holds only what the
guest was already given: the hostname, the authorized public keys, and any
user-data the operator passed. Nothing secret may be put there — that was
already true when the seed was an ISO the guest read at boot, and SECURITY.md
says so — but the window in which a guest can read it is now the VM's whole
life rather than its first seconds. A guest that wanted the same bytes could
read them from `/var/lib/cloud` regardless.

**Device topology changed.** A VM now has a second virtio disk. That is a
public contract (AGENTS.md §8): anything counting a guest's disks, or assuming
`vdb` is free, sees a difference. Existing VMs are unaffected — their domains
are already defined — but they cannot be compared device-for-device with new
ones.
